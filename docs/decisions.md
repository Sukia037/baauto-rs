## 移除晚到上限（2026-10-12，使用者決定）

- **決定**：整組刪除 `allowed_lateness_ms`（7 項晚到上限）與引擎的晚到取消。所有動作晚到都照送；快／慢卡幀的第二個 Esc 一定送出。規格 §5 已同步修改。
- **理由**：慢卡幀把第二個 Esc 排在 50ms，最晚期限也是 50ms（容許值 0），計時器只要晚一點就取消，實際上不可能成功。50ms 是原版 AHK 慢卡幀的等待時間，不是量過的遊戲上限；取消後遊戲只收到一次 Esc、停在暫停畫面，比晚送更糟。停止、失焦、資源衝突、故障各有自己的取消路徑，安全性不依賴晚到上限。原版 AHK 是 `Esc → Sleep → Esc`，從不取消。
- **語意**：`escape_gap_ms` 從「[最短, 最長] 有效區間」改成「[快卡幀, 慢卡幀] 各自的固定等待」，不再要求前者 ≤ 後者。JSON 欄位名不變。
- **相容**：舊的預設按鍵 JSON 帶 `allowed_lateness_ms` 仍可讀入，內容忽略，下次存檔時移除；其他未知欄位仍然報錯。IPC `PROTOCOL_VERSION` 由 3 升為 4（`TickTiming` 版面改變），app 與 engine 必須一起更新。
- **一併移除**：`Report::LateCancelled`、GUI「晚到上限（進階）」群組、Windows 原生測試的 `BAAUTO_TEST_DOUBLE_ESC_LATENESS_MS`，以及 bench 校準為了避開第二個 Esc 期限而拉長 `gap_max` 的特例。
- **待決定**：bench 的 `escape_gap` 校準結果目前仍寫成 `[selected, selected + margin]`（沿用區間語意）。改成固定等待後，應決定校準要分別量快／慢卡幀，還是只寫入其中一個。
- **接收器已驗收（2026-10-12）**：`tests/windows/M6.ps1 -Interactive` 在隔離替代全域熱鍵下通過，正式範本慢卡幀 50ms 等待實際收到兩組完整 Esc。預設熱鍵輪等待 Armed 逾時，首頁確認顯示佔用警告並停用啟用；遊戲仍未驗收。原始 CSV、profile 與兩輪 log 見 [互動報告](test-results/windows-20261012/interactive/README.md)。

## 牌鍵改為按住循環（2026-10-12，使用者更正）

- **問題**：規格 v0.4 把牌鍵寫成「按一下、送一次游標所在格的數字鍵、不移動游標、不點擊」，與使用者實際用法不符。
- **決定**：牌鍵有自己的點位座標。按住熱鍵時像連點一樣循環：讀使用者游標在第幾張牌 → 送該格數字鍵 → 在點位點一下 → 游標回到使用者位置。游標不在手牌上時暫停（使用者選擇）。時間共用連點的週期、按鍵按住、技能鍵到點擊、點擊按住（使用者選擇），另加一欄「牌鍵回位等待」`card_return_wait_ms`（預設 16ms），回位和下一輪按鍵階段重疊，所以預設速度和連點相同。
- **理由**：Unity 遊戲通常每幀讀一次游標位置；放開左鍵後立刻移走游標，點擊可能被算在牌上而不是點位上，所以點完要先停約一幀。
- **使用者游標**：游標被移到點位期間，Hook 記下移動前的位置並累加實體滑鼠位移，回位時移到這個位置，按住時仍可換牌。其餘時間用 `GetCursorPos`。
- **相容**：點位檔的牌鍵加上 `x`、`y`；沒有座標的舊牌鍵可以讀入，但停用並標示「需要錄點位」。舊 AHK 的拖曳點位匯入時，終點座標變成牌鍵點位。`settings.json` 的 `card_auto_repeat` 讀入後忽略、存檔時移除；舊預設按鍵檔缺 `card_return_wait_ms` 時用 16ms。`PROTOCOL_VERSION` 升為 5。
- **行為細節**：牌鍵按住期間持有滑鼠資源，普通點位、滑鼠連點要等它放開；該格數字鍵被其他動作按住時這一輪等待，不拒絕。緊急停止只放開按鍵，不移動游標。
- **待驗收**：Windows 接收器的牌鍵案例改為檢查循環順序、每次點擊都在點位、放開後游標回到牌上；需重跑 `tests/windows/M6.ps1 -Interactive`。「牌鍵回位等待」16ms 是否足夠，要在真實遊戲確認。
