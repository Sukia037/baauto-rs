BAauto-rs 架構

按鍵到遊戲的熱路徑留在同一個程序裡，維持最短；外面再包一個獨立的監督程序，引擎出事時由它先確認引擎停了，再放開按鍵。所有時間參數都可以設定，遊戲能承受的最低間距交給校準模式實測。

  • 熱路徑只在一個程序裡從鉤子到 SendInput 不經 IPC、不加鎖、不配置記憶體。
  • 狀態只有一個擁有者執行中的動作只歸引擎執行緒管，其他執行緒只傳訊息。
  • 出事由外面收拾監督程序先確認引擎已經停下或結束，才放開按鍵。
  • 間距是量出來的程式不寫死任何時間；最低間距用校準模式在遊戲裡量。

程序與資料流

一次按鍵的路徑

以「按下 W → 送出技能 1」為例。

  1. Windows實體按下 W

    系統在鉤子執行緒上呼叫 kb_hook。

  2. Hook Thread查表並交出事件

    略過自家注入，確認遊戲在前景，讀觸發表命中「技能 1」，push 進佇列並 SetEvent，回傳「攔截」。

    目標 < 50 µs
  3. Engine Thread立刻醒來處理

    從 WaitForMultipleObjects 返回，step() 產生「按下 1」和「放開 1」。按住時間設為 0 就合成一批，不為 0 就分兩次送。

    目標 < 0.2 ms
  4. Driver記帳、送出、核對

    先在帳本記下「1 可能按著」，呼叫 SendInput，確認回傳筆數，放開送出後才清帳本。

  5. BlueArchive.exe下一次讀輸入時收到

    這一段多久、按住要多長才不會漏，由遊戲決定，用校準模式量。

µs、ms 數字都是設計目標，還沒有實測；實作後用環形紀錄量。

元件與實作方式

時間關鍵路徑（程序 B）

Hook Thread鉤子執行緒融合
  • SetWindowsHookExW 掛 WH_KEYBOARD_LL、WH_MOUSE_LL，這條執行緒只跑 GetMessageW 迴圈。
  • callback 依序：帶自家 dwExtraInfo 標記的注入、滑鼠移動 → 立刻放行；更新實體按鍵位元集（自動重複只算第一次 Down）→ 遊戲在前景、滑鼠鍵還要游標在遊戲矩形內 → 查觸發表 → push ＋ SetEvent。
  • 把「最後一次被呼叫的時間」寫進共享記憶體，給監督判斷鉤子還在不在。
  • 整段包在 catch_unwind，panic 時放行。刻意不攔 Ctrl+F9、Ctrl+F10。
鉤子逾時太多次會被 Windows 悄悄移除，程式不會知道。callback 只做固定、很短的工作，就不會逾時。
Trigger Table觸發表新增
  • 固定大小的陣列：每個虛擬鍵（含 5 個滑鼠鍵）一格 AtomicU32，記錄哪些修飾鍵組合要攔截。
  • 控制執行緒用 seqlock 更新：寫入前後各把版本號加 1；鉤子讀到奇數或前後版本不同就重讀。
  • 只在引擎停止時更新，平常鉤子讀到的版本不會變。
v0.1 讓鉤子用 ArcSwap 讀設定，舊設定的最後一個參考可能剛好在 callback 裡被釋放。改成固定陣列後，鉤子裡沒有任何記憶體配置或釋放。
Event Queues事件佇列Astra
  • 兩條 rtrb SPSC：鉤子 → 引擎（按鍵＋焦點），控制 → 引擎（指令）。一條佇列只有一個生產者。
  • 容量 4096，啟動時配置一次，push 不配置記憶體。
  • 推不進去時：設 OVERFLOW 旗標並喚醒引擎，引擎進入安全停止。GUI 顯示發生次數。
v0.1 在佇列滿時直接放行；如果放行的剛好是放開事件，引擎永遠收不到，連點就停不下來。
Engine Thread引擎執行緒融合
  • 唯一擁有：執行中的動作、左鍵擁有者、帳本寫入權、遊戲矩形副本、目前的設定。
  • 迴圈：WaitForMultipleObjects([喚醒, 計時器, STOP]) → 最多處理 64 個事件 → step(now) → Driver → 更新心跳。
  • 每個動作自己記 next_at，計時器設到所有動作裡最近的那個；動作一刪，期限就跟著消失。
  • 每圈對照實體按鍵位元集：觸發鍵已經放開的動作直接停掉。
  • epoch：停止或換設定時加 1，停止前已經排隊的事件一律丟棄。
不需要另外的計時事件堆積，也就沒有舊計時事件復活的問題。每圈處理量有上限，突發輸入不會讓到期的動作一直被延後。
Precise Timing精準計時融合
  • CreateWaitableTimerExW 加 CREATE_WAITABLE_TIMER_HIGH_RESOLUTION；時鐘一律用 Instant（QPC）。
  • 卡幀這類精準動作：計時器等到截止前約 0.5ms，剩下用 spin 補；spin 每圈檢查 STOP。0.5ms 是校準前的預設值。
  • 啟動時用 SetProcessInformation 關閉電源節流，也關閉「忽略計時精度要求」。
  • 鉤子 THREAD_PRIORITY_TIME_CRITICAL、引擎 THREAD_PRIORITY_HIGHEST；程序維持一般優先權。
kanata 用 REALTIME_PRIORITY_CLASS 加 timeBeginPeriod(1)；這裡不照搬，避免跟遊戲搶 CPU。要不要再提高，看校準第 1 層的數字。
Action Model動作模型融合
  • enum Action：Tap、DoubleTap、Repeat、Card、Hold、Drag。
  • 每種動作有自己的時間語意，見下一節。
  • 多個拖曳輪流使用左鍵，每圈完整走完才交出；左鍵被持有時連點略過。
  • 所有間隔與按住時間都從 timing profile 讀。
非法狀態用型別寫不出來；時間語意跟著動作類型走，排程器不用猜。
Driver輸出層＋帳本融合
  • 同一時刻的輸出合成一次 SendInput；需要間隔的步驟一定分開送。
  • 先記再送：送 Down 前先在共享記憶體帳本設位元，Up 送成功後才清掉。帳本永遠是「可能還按著」的超集。
  • 核對回傳筆數；少於送出的筆數就標記 Faulted 並停止。
  • 送出前再看一次 STOP 和前景旗標；每筆帶自家 dwExtraInfo 標記。
  • 滑鼠用 MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK；0–65535 的換算要對到正確像素，測試時用 GetCursorPos 核對。
同一次 SendInput 的事件不會被其他輸入插進來，但兩次呼叫之間會。引擎被終止時，監督讀帳本就知道要放開哪些鍵。
Control Thread控制執行緒Astra
  • 用 overlapped Named Pipe 收設定與啟停指令，把狀態快照回傳給介面。
  • 換設定：確認引擎已停止 → 更新觸發表 → 把新設定交給引擎 → 回報版本。舊設定的記憶體由控制執行緒釋放，引擎不跑大型解構。
  • 收到「重新掛鉤」：PostThreadMessage 叫鉤子執行緒重掛。
  • 同時等待介面程式的 process handle：介面結束 → 停止、放鍵、自己結束。
引擎執行緒從不等待管線或介面，介面卡住也不影響輸出。

監督與紀錄（程序 A ＋ 共享記憶體）

Supervisor監督執行緒融合
  • 每 50ms 讀共享記憶體：引擎心跳超過 250ms → 執行停止協定。
  • 只在遊戲在前景時，比對 GetLastInputInfo 和鉤子最後呼叫時間；差太多就請引擎重新掛鉤，失敗就重啟引擎。
  • RegisterHotKey：Ctrl+F9 緊急停止、Ctrl+F10 錄點，不依賴低階鉤子。
  • 引擎結束後：依帳本放鍵 → 倒出環形紀錄 → 重啟成「未啟用」。
引擎如果只是變慢，可能在監督放鍵之後又醒來按下。先確認它停了或結束了，再放鍵。
Flight Recorder環形紀錄融合
  • 放在共享記憶體。每筆記：收到時間、預定期限、SendInput 前後時間、epoch、動作階段、回傳筆數。
  • 寫入只是記憶體寫入，不呼叫系統；引擎不寫檔。
  • 引擎被終止也讀得到；監督把它倒成檔案，可以直接丟回測試重播。
  • 校準第 1 層的數字也從這裡算。
出問題時能分辨是我們的邏輯、系統排程，還是遊戲沒吃到輸入。

設定與介面（程序 A）

Config Pipeline設定管線融合
  • serde 模型 → 編譯：熱鍵正規化成 Chord { mods, key }、衝突分析、拒絕把左鍵設成觸發鍵 → 觸發表＋動作表。

  • 換設定一定走停止協定，不在動作進行中換。
衝突用結構比對，不比字串；引擎不會讀到一半新、一半舊的設定。

  • 舊 AHK 檔：保留「相對鎖定螢幕」的意思，匯入時標記，GUI 詢問要不要轉換。

時間語意

引擎晚醒的時候怎麼辦，三種動作答案不一樣。這是兩份設計裡最值得保留的 Astra 論點。

參數用在AHK 版校準前的預設
repeat.period技能連點、滑鼠連點、卡幀開牌1ms 計時器，實際約 15.6ms16ms
key.hold送出按鍵時，按下到放開0（同一次 Send）0ms
drag.gap拖曳的按下→移動、移動→放開、放開→下一圈20／20／20ms（實際約 31ms）20／20／20ms

AHK 欄的「實際」是 Windows 預設 15.6ms 計時粒度下的推算值。預設值只是起點，校準後會被 timing profile 取代。

停止協定

放開熱鍵屬於一般停止，由引擎自己處理：刪掉動作，如果它正持有左鍵就送 LEFTUP。下面是緊急停止或引擎心跳逾時時的流程。

  1. Supervisor

    設定具名的 STOP Event。這一步不經過 Named Pipe，管線塞住也停得了。

  2. Engine

    從等待或 spin 中醒來，進入 Stopping：不再開始新動作、epoch 加 1、送出帳本裡所有鍵的放開、清帳本，最後在共享記憶體寫入 Stopped。

  3. Supervisor

    等 Stopped，最多 150ms（可調）。等到了就跳到第 5 步。

  4. Supervisor

    逾時：TerminateProcess 引擎，WaitForSingleObject 確認它真的結束，再依帳本送出放開。

  5. Supervisor

    把環形紀錄倒成檔案，重啟引擎並進入「未啟用」。

  6. Engine

    等所有綁定鍵都放開，才接受新的按下。不會自動恢復連點。

這套協定保證不了的事 已經送進 Windows 的事件不能撤回。焦點檢查和 SendInput 之間仍有極短的空窗。帳本是「可能還按著」的超集，所以放鍵時也可能放掉你正用手按著的同一個鍵。

校準：量出遊戲能承受的最低間距

程式這端能做到 0.1ms 等級，但遊戲多快讀一次輸入、按住多久才不會漏，只能在遊戲裡量。量的時候分三層，各自決定不同的參數。

每種動作的最低間距和按住時間
  1. 選目標

    選一種動作和要看的畫面區域。例如卡幀暫停看暫停選單有沒有出現，技能連點看技能有沒有發動。

  2. 從安全值開始

    例如 50ms。每個間距連續跑 200 次以上，記錄成功率和延遲分布。

  3. 往下搜尋

    用二分搜尋找出成功率 ≥ 99.5% 的最小間距（建議值）。按住時間和間距分開找，拖曳三段也分開找。

  4. 加安全邊際

    建議取第 1 層 P99.9 誤差的 2 倍，至少 2ms，存成 timing profile。

  5. 條件變了就重測

    改了遊戲幀率、解析度、視窗模式，或換電腦、換顯示器，都重跑一次，存成不同的 profile。

遊戲要用視窗或無邊框模式，DXGI 才擷取得到。校準請在練習關卡這類非排名內容進行。校準指令由介面送給引擎，影像分析在程序 A 做，都不在熱路徑上。

遊戲失焦WinEvent 前景事件，和按鍵事件走同一條佇列鉤子停止攔截；引擎停止所有動作、放開所有按鍵
放開事件遺失引擎每圈對照實體按鍵位元集停掉觸發鍵已經放開的動作
佇列滿push 失敗 → OVERFLOW 旗標安全停止，所有鍵放開後才重新啟用；GUI 顯示次數
鉤子被 Windows 拔掉監督：遊戲在前景時，GetLastInputInfo 比鉤子最後呼叫時間新太多停止所有動作，請引擎重新掛鉤；掛不回來就重啟引擎
引擎卡住或變慢心跳超過 250ms 沒更新停止協定：先確認停止或結束，再放鍵
引擎 panic迴圈外層的 catch_unwind放鍵、標記 Faulted、結束；監督重啟成未啟用
鉤子 callback paniccatch_unwind當作放行。Rust 1.81 起，panic 穿出 extern "system" 函式會直接 abort，所以一定要在 callback 裡接住
SendInput 筆數不足回傳值少於送出的筆數標記 Faulted、停止，記下 GetLastError
遊戲權限比較高被 UIPI 擋下時，回傳值和 GetLastError 都不會說原因，所以啟動時先檢查遊戲的完整性等級GUI 提示：本程式也要以系統管理員身分開啟
介面程式結束引擎控制執行緒等待介面的 process handle引擎自己停止、放鍵、結束；Windows 移除它的鉤子
拖曳中視窗移動EVENT_OBJECT_LOCATIONCHANGE取消這一圈拖曳，放開左鍵
按下 Ctrl+F9RegisterHotKey，不經過低階鉤子停止協定，然後結束兩個程序

測試策略

  • core 是純邏輯：引擎吃「事件＋假時鐘」，吐出「輸出列表」，不用開遊戲就能測。
  • proptest 不變量：LEFTDOWN／LEFTUP 永遠成對；同一時間最多一個左鍵擁有者；失焦後沒有按住的鍵；連點間隔和拖曳每段間隔都不小於設定值（晚醒也一樣）；停止確認之後沒有任何輸出；舊 epoch 的事件不產生輸出。
  • Loom：觸發表的 seqlock、OVERFLOW／STOP 旗標、帳本「先記再送」的順序。
  • 重播：環形紀錄倒出來的檔案直接變成回歸測試。
  • 故障注入（Windows 實機）：拖曳途中殺掉引擎；手動 UnhookWindowsHookEx 模擬鉤子被拔；塞滿佇列；讓 SendInput 失敗；讓引擎故意卡 300ms 再恢復，確認監督放鍵之後它不會再按下。
  • 長時間測試：多鍵交錯連續跑 8 小時，看 P99.9 與最差延遲，以及有沒有任何卡鍵。

里程碑

校準排在 GUI 前面，因為量出來的間距會決定這套設計夠不夠用。

  1. core：動作狀態機、時間語意、epoch，用假時鐘和 proptest 驗證。完全不碰 Windows。

  2. 引擎程序熱路徑：鉤子、觸發表、佇列、Driver，加上共享記憶體的帳本和環形紀錄。

  3. 監督程序：停止協定、緊急停止、心跳、重新掛鉤，跑一輪故障注入測試。

  4. 校準模式：先量第 1 層，再量遊戲的最低間距，寫出第一份 timing profile。

  5. GUI：編輯器、錄點、匯入舊 JSON 與 MuMu。

  6. 長時間測試：8 小時多鍵交錯，確認最差延遲和零卡鍵。

從 kanata 借了什麼

以下對照 kanata 目前 main 分支的原始碼。

借用的設計
  • 輸入迴圈和處理迴圈分在不同執行緒，中間用有界通道。
  • 判斷時間到了沒看單調時鐘，不靠 sleep 的精度。
  • 平台 I/O 抽象成 trait，核心邏輯可以單獨測試。
不借用
  • 核心包在 Arc<Mutex> 裡：這裡由引擎執行緒獨占。
  • REALTIME_PRIORITY_CLASS 加 timeBeginPeriod(1)：這裡用高精度計時器，程序維持一般優先權。
  • 部分延遲直接 thread::sleep：這裡只排下一個期限，等待期間還能處理停止。
  • 巨集重複與取消的語意：kanata 同時按住多個重複巨集只重複最後一個，取消時一次取消全部。
  • 程式碼本身：kanata 是 LGPL-3.0，只參考設計。
